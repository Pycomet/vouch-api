# Vouch API — Milestone 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Stop and report after each Step (PR) — do not start the next Step until the user says go.**

**Goal:** Move `vouch-api` from a read-only Lagos inventory to a working booking backend for Abuja. It adds reference tables, a catalogue, the booking state machine, an append-only ledger and audit log, phone OTP, and provider interfaces with fakes. It ships as 6 PRs against `main`.

**Architecture:** This extends the existing FastAPI modular monolith (`src/app/{api,core,db,schemas,services}`). The database enforces the invariants: CHECK constraints, foreign keys, the gist exclusion constraint, append-only triggers and a deferred balance trigger. Services run every transition in a single transaction with `SELECT … FOR UPDATE`. Providers sit behind `Protocol` interfaces, and only fakes exist.

**Tech stack:** Python 3.11, FastAPI, SQLAlchemy 2.0 async with asyncpg, Alembic, Postgres 16 (btree_gist), pytest/pytest-asyncio, ruff. One new runtime dependency: `pyjwt>=2.8` (Step 4).

**Spec:** `docs/specs/M2.md` (the pasted "Vouch Backend Spec — Milestone 2", v1.0, 28 Sept 2026), read together with the agent brief and the **Amendments** section below. Where the spec says "0002", read **0003**.

## Global constraints (every task inherits these)

- Money: `Numeric(12,2)`, currency `NGN`, Python `Decimal` only. Quantize with `Decimal("0.01")` and `ROUND_HALF_UP`. Serialize money as strings `"150000.00"`. No `float` anywhere money is involved (enforced by a test that greps `src/app` for `float(` in services and schemas).
- No Paystack, Flutterwave or KYC SDK in `pyproject.toml`. Fakes only.
- The two words banned by brief rule 7 never appear in identifiers, comments, API fields or docs (enforced by `tests/test_wording.py`, which greps `src docs migrations tests README.md` and excludes `docs/specs/M2.md`, the verbatim spec).
- Reference slugs are exactly `abuja`, `lagos` and `camera`, `lens`, `lighting`, `audio`, `drone`, `gimbal`, `accessory`.
- Every booking transition writes ≥1 `audit_events` row. Every money movement writes a balanced `txn_group` in `ledger_entries`. Corrections are reversing entries.
- Live booking statuses are defined **once** as `LIVE_BOOKING_STATUSES` in `app/db/models/booking.py` = `requested, accepted, deposit_paid, confirmed, in_progress, returned`. The exclusion constraint WHERE clause and inventory both use it.
- Out of scope: web client, WhatsApp adapter, search ranking, reviews, disputes UI, kits, delivery zones.
- Secrets live only in `.env.example` placeholders (`VOUCH_JWT_SECRET=change-me`, `VOUCH_FAKE_PAYMENT_WEBHOOK_SECRET=change-me`).
- Each Step is one branch `m2/stepN-<slug>` and one PR into `main`, with small commits. Commit as the user (load the `commit-as-me` skill, so no Claude co-author trailers).
- Verification gate before every PR: `ruff format --check . && ruff check . && VOUCH_TEST_DATABASE_URL=… pytest --cov=app` must be green, coverage ≥90%. Local Postgres: `docker run -d --name vouch-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=vouch_test -p 5432:5432 postgres:16`.
- Budget: Steps take 0.2 / 2 / 3 / 1.5 / 1.5 / 0.3 days. If a Step passes 1.5× its estimate, stop and report.

## Review focus (failure modes the spec implies but doesn't spell out; each has a test in its owning task)

1. **Timezone at date boundaries.** `starts_on`/`ends_on` are dates in `Africa/Lagos` (WAT, UTC+1), while `now()` is UTC. "Before starts_on" means before 00:00 WAT on `starts_on`. → Task 3.4 `test_cancel_at_2330_utc_day_before_start_is_refused`.
2. **Deadline exactly at expiry.** Accepting at `now == hold_expires_at` must give 409, because guards use strict `now < deadline`. The timer and a vendor action racing on one booking must not both win. → Task 3.2 `test_accept_at_exact_hold_expiry_is_409`, Task 3.5 `test_timer_and_accept_race_one_wins`.
3. **Money arriving after a booking died.** A `deposit_captured` webhook for an `expired` booking still moved real money. Record the capture, post an immediate reversing refund txn, write audit `deposit.refunded_late`, and leave the state `expired`. → Task 5.3 `test_late_deposit_is_recorded_and_refunded`.
4. **Hostile money input.** Claim amounts like `"1e3"`, `"-5"` or `"10.001"` and float JSON values return 422. A claim larger than the deposit is accepted, but the deduction is capped at the deposit. → Task 4.2 `test_claim_amount_validation`, Task 3.4 `test_resolve_deduct_capped_at_deposit`.
5. **Self-dealing and frozen users.** A renter booking their own asset is blocked by DB CHECK `renter_id <> vendor_id`. A user with `restricted_at` set cannot request. → Task 2.4 `test_self_booking_rejected_by_db`, Task 3.2 `test_restricted_renter_cannot_request`.

Rate basis: `weekly` if the span is ≥7 days and `weekly_rate` is set (`full_weeks*weekly_rate + remaining_days*daily_rate`); `weekend` if the span is exactly Fri–Sun and `weekend_rate` is set; else `daily*days` (days inclusive). It also holds `delivery_fee`, `deposit`, `commission_rate`, `damage_contribution` (rate × rental, quantized, or "0.00"), `rental_total`. All values are strings.
- `async request_booking(session, *, renter: Actor, asset_id, starts_on, ends_on, fulfilment: Literal["pickup","delivery"], damage_contribution: bool, clock, notifier, settings) -> Booking`. Guards in order: asset public in a launched city (else 404); dates valid and `starts_on ≥ today (business tz)`; renter not restricted; tier; no blocked window; insert (a DB exclusion violation becomes `dates_unavailable`). Sets `hold_expires_at = now + 4h` and writes audit `booking.requested`.
- `async transition(session, booking_id: UUID, actor: Actor, event: BookingEvent, payload: Mapping[str, Any] | None = None, *, clock, notifier, settings, provider=None) -> Booking`. Loads with `.with_for_update()`, looks up `(status, event)` in a `_TRANSITIONS` dict of handler functions, checks the actor role per the §3.1 table (renter/vendor must be the booking's own party), runs the handler, writes the audit row `booking.<to_status>` with before/after `{status}` (+ the changed columns), and flushes. The caller owns the commit. Anything missing → `InvalidTransition`, and nothing is written.
- Handlers in this task: accept (`now < hold_expires_at`; sets `deposit_due_at = now+12h`; calls `provider.create_virtual_account` if a provider is given), decline, approve_vendor (vendor sets `vendor_approved_at` while `requested`; this is what allows a tier-3 asset to be accepted), expire_hold.
- Tier-3 rule: `request` is allowed if effective ≥2. **`accept` on a min-tier-3 asset requires `vendor_approved_at`, else `vendor_approval_required`.** This satisfies the §2.7 test: "band-C without vendor_approved_at is refused".

### Task 3.3: Money transitions

**Files:** modify `booking.py`; create `src/app/services/money.py` (posting recipes); tests `tests/postgres/test_booking_money.py`.
**Produces:** posting recipes. Each is a pure function returning `list[Posting]`. With D = deposit, C = damage contribution, R = rental, F = delivery fee, and K = (R × commission_rate) quantized:
- `deposit_captured_postings(D, C)`: dr platform_cash D+C / cr renter_deposit_liability D / cr protection_pool C (lines with 0 omitted).
- `balance_captured_postings(R, F, K)`: dr platform_cash R+F / cr vendor_payable R+F−K / cr platform_revenue K.
- `deposit_release_postings(D)`: dr renter_deposit_liability D / cr platform_cash D.
- `deposit_deduct_postings(D, X)`: X capped at D; dr liability D / cr vendor_payable X / cr platform_cash D−X.
- `deposit_forfeit_postings(D)`: dr liability D / cr vendor_payable D.
- `refund_contribution_postings(C)`: dr protection_pool C / cr platform_cash C.
- `payout_postings(P)`: dr vendor_payable P / cr platform_cash P.

Handlers:
- `deposit_captured` (payload `amount`, `payment_id`): requires `amount == D + C`, else `BookingGuardFailed("amount_mismatch")`. Steps through deposit_paid → confirmed, writing **two** audit rows; posts; notifies both parties.
- `expire_deposit`.
- `cancel` (renter: requires `now < start_of_business_day(starts_on)`, then refunds D and C in full per A8; vendor: any time from confirmed, full refund, audit action `vendor.reliability_penalty`).

Tests: each posting function sums dr == cr (parametrized, with Decimal edge values like `"0.01"` and `"9999999999.99"`); `test_deposit_captured_confirms_and_posts` (liability = D); `test_deposit_amount_mismatch_no_transition`; `test_renter_cancel_refunds` (liability back to 0); `test_cancel_at_2330_utc_day_before_start_is_refused`; `test_vendor_cancel_any_time`.

### Task 3.4: Handover, return, claim, resolve, lost

**Files:** modify `booking.py`; tests `tests/postgres/test_booking_lifecycle.py`.

- `handover_completed` and `balance_captured` each record their fact (the handover record is completed, or a captured `rental_balance` payment exists). The handler moves to `in_progress` only when **both** hold. Otherwise the state stays `confirmed`, with audit `booking.handover_signed` or `booking.balance_captured`. `balance_captured` posts `balance_captured_postings`.
- `return_completed`: `claim_window_ends_at = now + 24h`.
- `claim_raised` (vendor, `now < claim_window_ends_at`, payload amount/description/evidence) sets the claim columns and moves to `disputed`.
- `complete` (system, `now ≥ claim_window_ends_at`, no claim): deposit release postings and audit `deposit.released` + `booking.completed`.
- `resolve` (admin, reason required, `decision ∈ {release, deduct, forfeit}`, `amount` for deduct): moves to `completed` and posts the matching recipe.
- `flag_at_risk` (system): sets `at_risk_at` and the renter's `restricted_at`/`restricted_reason="at_risk"`. The state does not change, but an audit row is written.
- `mark_lost` (admin, reason required, `now ≥ start_of_business_day(ends_on + 7d)`): forfeit postings and renter `restricted_reason="lost_item"`.
