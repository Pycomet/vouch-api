# Vouch Data Schema

## 1. Purpose and notation

This document separates the **current migrated schema** from **planned v1 additions**. The source of truth for what exists today is the SQLAlchemy model set and `migrations/versions/0001_initial_schema.py`; planned tables below require future migrations.

- **Current**: exists in models and initial migration.
- **Planned**: contract-level design, not implemented.
- **Money rule:** every amount is `Numeric(12,2)` in `NGN` in the database and Python `Decimal` in code. Never use floating point, and never do arithmetic outside `Decimal` (quantize to `Decimal("0.01")`, `ROUND_HALF_UP`). APIs serialize amounts as decimal strings such as `"150000.00"`.
- All timestamps are timezone-aware and should be written/read in UTC.
- UUID primary keys are generated by PostgreSQL.

The current migration enables `pgcrypto` for `gen_random_uuid()` and `btree_gist` for booking overlap exclusion.

## 2. Relationship map

```text
users ──1:0..1── kyc_profiles
  │
  ├──1:N── assets ──1:N── availability_windows
  │                  └──1:N── bookings
  ├──1:N──────────────────┘ (renter)
  └──1:N── handover_records (vendor/renter signer)

bookings ──1:N── payments
    └──────1:N── handover_records (max one per direction)

Planned:
users/bookings/payments/handovers ──1:N── audit_events
provider deliveries ──1:1+── webhook_events
bookings ──1:N── disputes
bookings ──1:N── booking_financial_entries
handover_records ──1:N── evidence_objects
kyc_profiles ──1:N── kyc_attempts
```

## 4. Current tables

Every current table has `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` and `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` through `TimestampMixin`. Application updates are expected to set `updated_at`; there is no database update trigger.

### Table: `users` — current

| Column | Type | Rules |
|---|---|---|
| `id` | UUID | PK, `gen_random_uuid()` |
| `phone` | VARCHAR | NOT NULL, UNIQUE, indexed |
| `full_name` | VARCHAR | NOT NULL |
| `email` | VARCHAR | nullable, UNIQUE |
| `role` | `renterrole` | NOT NULL; Python default `renter` |
| `is_active` | BOOLEAN | NOT NULL; Python default `true` |
| `deleted_at` | TIMESTAMPTZ | nullable soft-delete marker |
| `created_at`, `updated_at` | TIMESTAMPTZ | audit timestamps |

Notes: soft deletion must exclude deleted users from normal queries. The schema does not normalize phone numbers, preserve terms acceptance, or support multiple roles; these are application/planned concerns.

### Table: `kyc_profiles` — current

| Column | Type | Rules |
|---|---|---|
| `id` | UUID | PK |
| `user_id` | UUID | FK `users.id`, NOT NULL, UNIQUE |
| `provider` | VARCHAR | NOT NULL |
| `provider_reference` | VARCHAR | nullable |
| `status` | `kycstatus` | NOT NULL; Python default `pending` |

| `national_id_type` | VARCHAR | nullable |
| `verified_at` | TIMESTAMPTZ | nullable |

The code's tier policy requires national ID + liveness for tier 1 and those checks plus address for tier 2. The database constrains tiers to `0..2`, requires `verified_at` for verified profiles, and keeps non-null provider references unique. The table still stores a mutable outcome only; it lacks attempt history, provider-event deduplication, review reason, and provenance for individual checks.

## 5. Current lifecycle invariants

### Booking

| State | Entry invariant | Allowed next states |
|---|---|---|
| `pending` | Valid pricing/dates and eligible renter must be enforced by service | `confirmed`, `cancelled` |
| `confirmed` | Required approval + verified deposit | `active`, `cancelled`, `disputed` only if policy permits |
| `active` | Verified balance + completed pickup | `completed`, `disputed` |
| `disputed` | Open documented exception; money movement blocked | `completed`, exceptionally `cancelled` |
| `completed` | Completed return and settlement eligibility determined | terminal |
| `cancelled` | Cancellation timestamp/reason set | terminal |

Only overlap prevention is currently database-enforced; the other transition gates are planned service rules.

### Handover

| State | Meaning | Allowed next |
|---|---|---|
| `draft` | Mutable checklist/evidence preparation | `vendor_signed`, `renter_signed` |
| `vendor_signed` | Vendor signature recorded | `completed` after renter signature/evidence |
| `renter_signed` | Renter signature recorded | `completed` after vendor signature/evidence |
| `completed` | Both signatures/timestamps and evidence present | terminal; corrections append audit/evidence records |

### Payment, deposit, and payout

| Aggregate | State progression |
|---|---|
| Payment row | `pending → authorized → captured`; `pending/authorized → failed`; `captured → refunded` |
| Deposit policy | `held → released` or `held → claimed`; persisted on deposit payment rows with lifecycle timestamps |
| Payout policy | `pending → eligible → paid`; persisted on payout rows, with eligibility gated by a completed return in domain policy |

These state columns support Phase 0 controls but do not replace provider reconciliation, an immutable financial ledger, dispute holds, idempotent commands, or audited transition services; money movement remains concierge-gated until those controls exist.

## 6. Planned v1 schema additions

Names and columns are recommended contracts and may be refined in reviewed migrations. They must preserve compatibility with current tables.

### 6.1 Planned changes to current tables

| Table | Planned additions |
|---|---|
| `users` | normalized phone, terms/privacy version and acceptance timestamps; consider role memberships only if multi-role is approved |
| `kyc_profiles` | last review reason, provider-decision timestamp; provider remains Smile ID/Dojah until selected |
| `assets` | listing status (`draft/review/active/paused/rejected`), review actor/time/reason, optional minimum renter tier |

## 7. Index and constraint plan

In addition to current indexes:

- partial/search indexes on active, non-deleted assets by `city`, `category`, and rate;
- index bookings by `(renter_id, created_at)`, `(asset_id, starts_on, ends_on)`, and `(status, updated_at)`;
- unique provider references scoped by provider rather than globally if multiple providers become possible;
- unique webhook dedupe and idempotency keys;
- indexes on unresolved disputes, unreconciled transactions, eligible payouts, pending outbox jobs, and evidence expiry;
- check constraints for currency `NGN`, valid trust tiers, non-negative commission/tax/refund components, paired coordinate nullability, and lifecycle-consistent timestamps where practical; and
- preserve the existing GiST overlap constraint. The migration's `btree_gist` extension is required for it.

Service transactions must lock/version contested bookings when confirming, activating, settling, cancelling, or opening/resolving disputes.

## 8. Data classification and NDPA controls

| Class | Examples | Required controls |
|---|---|---|
| Public marketplace | Listing name, category, public description, rate, city | Moderation; no serial number/private contact leakage |
| Account PII | Name, phone, email | Encryption, role/ownership access, subject-rights workflow |
| Restricted identity | KYC reference/outcome, ID type, check results | Strict least privilege; no raw biometric/ID retention by default; access audit |
| Restricted evidence | Photos, signatures, location, condition notes | Private object storage, signed access, integrity hash, legal hold/expiry |
| Restricted financial | Provider refs, amounts, ledger/reconciliation | Least privilege, immutable history, no card/bank credential storage |
| Security/audit | request IDs, actor/action, safe diffs | Append-only protections and redaction |

Schema design must follow lawfulness, purpose limitation, minimization, accuracy, storage limitation, confidentiality, and accountability. Exact lawful bases, notices, retention periods, cross-border safeguards, and data-subject deletion exceptions remain unresolved pending counsel/DPO review.

## 9. Retention and deletion

No final periods are asserted here. Before launch, an approved schedule must cover users, KYC attempts/results, payment and accounting records, booking records, disputes, handover evidence, audit events, webhook payloads, logs, and backups.

- `users` and `assets` currently soft-delete; this is not erasure by itself.
- Financial, fraud, dispute, and legal records may require restriction/tombstoning rather than deletion.
- Evidence expiry must remove object data and retain only the minimum auditable tombstone unless legal hold applies.
- Backup expiry must follow the schedule; restoration procedures must reapply deletion queues where required.
- Legal hold is explicit, scoped, authorized, and audited.

Retention durations and deletion exceptions are **unresolved legal/compliance decisions**.

## 10. Backup, PITR, and recovery

Production PostgreSQL must use encrypted automated snapshots plus continuous WAL archiving for point-in-time recovery. Backups must be isolated from production credentials, monitored, and restore-tested before launch and at least quarterly. RPO and RTO remain to be approved. Private evidence object storage requires versioning/backup and lifecycle policies aligned with database retention. Restore drills must verify relational integrity, provider references, ledger totals, evidence object links/hashes, and audit continuity.

## 11. Migration and rollout rules

- Use reviewed Alembic migrations; never modify an applied migration.
- Prefer expand/backfill/verify/contract for production schema changes.
- Backfill planned financial/audit state before enabling automation.
- Validate enum changes carefully because PostgreSQL enum rollback is non-trivial.
- Keep provider-specific payloads at adapter boundaries; normalized domain columns drive business logic.
- Reconcile migration defaults with ORM defaults explicitly; several current defaults are Python-side only.
- Test constraints against a real PostgreSQL instance, including `pgcrypto`, `btree_gist`, JSONB checks, and exclusion behavior.
